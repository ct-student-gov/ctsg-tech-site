# Repository-backed website data

Activated on September 30, 2026: all four required GitHub Actions secrets are configured, the daily workflow is on main, and GitHub Pages serves 91 profiles and 87 calendar events. Two full cloud imports succeeded. The existing calendar JSON/ICS endpoint now serves these saved files, and its old polling cron is removed. Both Notion notification subscriptions are verified and active; the daily schedule works independently.

Notion is the editing source. The repository is persistent storage. The website serves saved public data and local WebP photos; visitors never trigger a Notion import. The existing calendar subscription URL remains available through a small compatibility Worker that fetches the published static ICS. Its old storage bindings remain untouched during migration, but the new handler does not use them and its six-hour cron is removed.

## Update flow

`.github/workflows/pages.yml` runs a full sync daily at 00:43 UTC, supports manual syncs, and accepts signed Notion notifications through the [Cloudflare relay](notion-webhook.md). GitHub can delay scheduled runs. Calendar notifications refresh the Notion calendar tables using stored query cursors; People notifications check the Team Directory. Neither notification refreshes unrelated Cornell feeds. Full daily runs also refresh the Cornell feeds. A first calendar import without any cache fills all sources.

The People metadata query detects newly published, unchecked and deleted profiles. Only changed biographies are reread. Photos are downloaded only when their attachment identity changes or a local file is missing/corrupt; temporary signed URL changes do not trigger downloads. Non-WebP uploads are converted locally by Sharp before publication. The Notion upload itself is not modified.

[Blog](blog.md) uses the same snapshot/body/photo caching and publication gate. The read-only Blog credential is configured and its live import is verified. `NOTION_BLOG_TOKEN` enables it in daily/manual jobs; its prepared webhook refreshes Blog only, and mixed notification batches list every affected source. The Blog notification subscription is not yet activated.

The calendar saves original per-source records before deduplication. Ended events remain in `data-sync/calendar.json` and appear in JSON/ICS even after disappearing upstream. Ordinary runs do not individually poll historical Notion pages; queries request recent edits and current/future dates. The short edit overlap may return a few unchanged records near the saved cursor. Explicit edits and received page notifications can correct or withdraw an archived Notion event. Missing/trashed historical pages cannot be discovered through the daily query if their notification is missed; archived history is intentionally retained in that case. Whole ICS feeds and calendar listing pages still have to be downloaded; known historical Tech detail pages are skipped.

Generated files are deterministic. No-op syncs do not commit or rebuild. Metadata-only changes can create a small state commit without a site build. Changed public data is built and image-validated before the bot commits it and deploys that same artifact. Bot commits made with `GITHUB_TOKEN` do not start a second workflow, so publishing is part of the same run. Queued builds use current main; concurrent human edits can cause a safe non-fast-forward push failure, leaving the deployed site intact for a later run.

Any import or build error leaves the deployed site intact. A Notion HTTP 429 stops the run without immediate retries; that failed run commits **only** `data-sync/backoff.json`. Subsequent triggers defer both Notion imports until the next UTC day. Other failures retry on a later notification/daily run. If GitHub itself cannot run/push because of a quota or outage, no backoff marker can be guaranteed, but the previously published static files remain available. Enable Actions failure notifications to see failures; notification preferences are not changed by this code.

Published snapshots keep their timestamp when their contents have not changed. The scheduled sync workflow, rather than snapshot age, establishes whether the latest check succeeded. The optional calendar health workflow checks public structure/coverage; it cannot prove that every source event exists or that a sync recently ran. GitHub may disable public-repository schedules after 60 days without repository activity, so verify the schedule at officer handoff, particularly during long quiet periods.

## Activation order

These steps describe recovery or setup in another deployment. The repository secrets, initial import, Pages publication and calendar Worker cutover below are complete for the current deployment.

1. Configure the remaining repository Actions secrets `NOTION_TOKEN`, `CAMPUSGROUPS_STUDENT_AFFAIRS_URL`, and `CAMPUSGROUPS_CAREER_MANAGEMENT_URL`. The optional `CAMPUSGROUPS_INCLUSION_BELONGING_URL` is supported. Reuse the existing approved read-only Calendar connection and existing student export URLs. The read-only People connection scoped to Team Directory and its `NOTION_PEOPLE_TOKEN` secret are already configured. Credentials stay in secrets, never in committed files. Their presence is checked so a missed credential cannot silently reduce the published data.
2. Ensure Actions may write repository contents and the normal validated Pages workflow may publish. A branch rule requiring reviews for every bot commit needs an explicitly approved exception or a different update branch; no branch protection is changed here.
3. Before cutover, use the complete secrets to run `npm run data:sync`, review the first saved roster/calendar/archive, then run `npm run check`, `npm test`, `npm run build`, and `npm run images:check`. The workflow also forces a complete first import if either repository state file is absent; missing secrets or a failed import prevent publication of the old/incomplete snapshots. The importer seeds history from the checked-in calendar snapshot and current source feeds. If the old live service has older events absent from both, export and merge those before retiring it. No already-discarded events can be recreated automatically.
4. After review/approval, publish the repository changes and run **Build and publish site** with **sync** enabled. Confirm the checked-in data and built site include all connected sources and published People. Do not switch the calendar proxy until the static files are live.
5. Deploy the compatibility calendar Worker with `npx wrangler@4.143.1 deploy --config calendar/wrangler.jsonc`. This removes its old cron and points the existing subscription URL at the published files. No old KV/Durable Object resources are deleted. If the static hosting path changes, update `CALENDAR_SNAPSHOT_BASE_URL` and `public/calendar-config.js`.
6. Set up and deploy the signed [Notion webhook relay](notion-webhook.md), then verify both subscriptions. Verify a biography edit, Publish withdrawal and calendar edit produce a sync commit and site update. Daily sync works before webhooks are connected. No connection or webhook is created automatically by a website build.

For local importer work, `npm run people:sync` and `npm run calendar:sync` use environment credentials. `npm run dev` and regular builds use the saved files without credentials. `CALENDAR_LOCAL_SOURCES=1 npm run dev` still exposes a live-import development API; it is not the production path.
